## Objective

A public GitHub portfolio project: an engine that takes a system described in plain language, translates it (via a small set of documented rules) into a declarative YAML graph of operations, and runs it as a scan-cycle simulation -- topologically sorted, not hand-ordered.

The core pitch: once a system is a plain declarative graph instead of hard-coded procedural logic, it stops being rigid. Capability gets added *around* the existing graph (a physics plant replacing a placeholder, a monitoring layer added on top) without rebuilding what's already there.

Demonstrated end-to-end on one running example: a single-car elevator serving six floors (widened from an originally-described three, specifically so `Elevator_System_2`'s motion profile has room to show a real cruise phase -- not because the elevator itself changed), taken through three stages of increasing requirement complexity, each a genuine upgrade rather than a rebuild:

- **`Elevator_System_1`** -- pure logic, translated from plain English. Motion between floors is a fixed-time placeholder; dispatch always serves the lowest-numbered pending call (not what a real elevator does -- see below).
- **`Elevator_System_2`** -- the placeholder motion is replaced with a real physics plant (position/velocity), so trip time becomes a genuine output of physics. This also makes real LOOK-algorithm dispatch possible for the first time (continue current direction, serve calls along the way, reverse only once nothing's left ahead) -- structurally impossible in `Elevator_System_1`, confirmed via an actual `CycleError`, not assumed.
- **`Elevator_System_3`** -- a CUSUM (cumulative-sum control chart) monitoring layer, comparing a nominal (healthy, kinematic) model's expectation against a second, independent physics plant's actual behavior (a genuine mass-spring-damper, not a repeat of the same model), to catch slow, usage-driven damping wear that a simple threshold would miss.

All three stages share one interactive tool (`example/elevator_viz.py`'s `run_interactive()`): click a floor to call the car, a Close Door button, Pause/Resume, and 1x/5x speed control. `Elevator_System_3` additionally gets an off-by-default Auto-Cycle toggle (the wear story needs dozens of round trips) and a fourth panel showing the full-run drift trend, since that story can't be told by a recent-scans window the way position/velocity can.

Origin note (goes in the README, not hidden): the project is not connected to or derived from any employer's proprietary system. It's motivated by a real friction point -- conceptually understanding an industrial control system is not the hard part; translating dense technical documentation into working simulation without PLC-specific fluency is.

## Current status

**Done:**

- GitHub repo created (public, MIT license), cloned locally over SSH (personal key, not tied to any institutional account), `.gitignore` in place.
- `README.md` at repo root -- written, includes the "why" framing above.
- `engine/` -- five files, all generic, none of them elevator-specific:
  - `evaluate.py`, `topological_sort.py`, `function_blocks.py`, `scan_cycle.py` -- unchanged since the original build.
  - `simulation_runner.py` -- new. `setup_simulation(yaml_path, scan_time)` does load/sort/seed without running anything; `run_scan_loop(...)` (batch, scenario_fn-driven) builds on it. Both are used: `run_scan_loop` for one-shot validation scripts, `setup_simulation` directly by the interactive engine, which steps scans itself in response to real button clicks instead of a pre-written scenario.
- `example/elevator_viz.py` -- shared across all three stages, deliberately not engine-generic (knows about floors/doors/buttons) but stage-generic (reads whatever tags exist in a given stage's history, degrades gracefully when they don't -- e.g. no velocity panel for `Elevator_System_1`, no monitoring panel outside `Elevator_System_3`). Two families of function:
  - Passive display (`animate_elevator`, `render_static_frame`, `show_live`) -- take an already-finished history dict, no engine dependency.
  - `run_interactive(...)` -- the live engine. Imports `run_scan` and actually drives the simulation, one scan per real timer tick, in response to: floor-call buttons (held internally until the floor's request is actually served, emulating a physical press held down, since dispatch reads the raw signal every scan rather than a remembered latch -- see `Elevator_System_1`'s note 1), a momentary Close Door button, Pause/Resume, and 1x/5x speed buttons (many scans run per tick, but the figure only redraws once per tick -- decouples simulated speed from redraw cost). `Elevator_System_3` additionally gets an Auto-Cycle toggle (off by default -- a manual click always takes priority) and a fourth "monitoring trend" panel, shown only when the stage's tags support it.
  - A "commanded vs. actual" readout, shown for every stage: `Moving` (what the logic commands) next to `Velocity_FloorsPerSec` (what the plant actually produces) -- for `Elevator_System_1` this explicitly says "no independent signal exists in this stage," since `Current_Floor` there is a CTUD the logic drives itself, not something separate to compare against.
- **`Elevator_System_1`** (`elevator_1.yaml`, `description_1.md`, `run_simulation1.py`) -- six floors (0-5), pure logic, fixed-time placeholder motion, lowest-numbered-call-wins dispatch. `description_1.md` is explicit about two real gaps between the plain-English intent and the translated logic: dispatch reads the raw call signal (not a remembered request), and the "priority order" isn't really an order at all -- it's a fresh lowest-floor decision every scan, so a car mid-flight toward floor 4 will reverse immediately if floor 1 gets called, confirmed by actually running that exact scenario.
- **`Elevator_System_2`** (`elevator_2.yaml`, `car_physics.py`, `description_2.md`, `run_simulation2.py`) -- `Current_Floor`/`Velocity_FloorsPerSec` moved to `runtime_inputs`, written every scan by an external kinematic (trapezoidal accel/cruise/decel) plant, never by an operation. This one change unlocks three things at once, not three separate features: (1) `Moving` becomes the plant's real run/hold command, not a display indicator, which also fixes `Elevator_System_1`'s note-2 mid-dwell-preemption gap for free; (2) a genuine commanded-vs-actual split exists for the first time, which is the actual precondition `Elevator_System_3`'s CUSUM needs; (3) real LOOK-algorithm dispatch becomes possible, since `Target_Floor` can now safely compare against `Current_Floor` without creating a cycle. All three physical constants (`Max_Velocity`, `Acceleration`, `Deceleration`) trace to a stated plain-English requirement in `description_2.md` (~2 seconds to accelerate / cross a floor / decelerate), not arbitrary Python defaults -- and `car_physics.py`'s constructor has no fallback defaults for any of them, so a missing constant fails loudly instead of silently substituting a number nobody asked for. `Close_Door_Button` added, wired into `Doors_Open`'s existing `Reset` list (already supported multiple OR'd conditions natively -- no new engine capability needed).
- **`Elevator_System_3`** (`elevator_3.yaml`, `car_physics_3.py`, `description_3.md`, `run_simulation3.py`) -- two independent physics plants every scan: `NominalPlant` (the unmodified `Elevator_System_2` kinematic model, writing `Nominal_Current_Floor`/`Nominal_Velocity_FloorsPerSec`, never authoritative) and `ActualPlant` (a genuine second-order mass-spring-damper, tracking the nominal plant's position/velocity as a moving setpoint, writing the authoritative `Current_Floor`/`Velocity_FloorsPerSec`). Wear degrades `ActualPlant`'s damping ratio slowly, proportional to time spent with `Moving=True` (usage-based, not calendar-time) -- a real, physically motivated failure mode. A CUSUM monitor (`Velocity_Residual` -> `Abs_Velocity_Residual` -> `CUSUM_High` -> `CUSUM_Alarm`) watches for the resulting drift, implemented as genuine declarative YAML operations, not Python -- see `docs/architecture.md`'s new "Stateless self-referencing accumulators" section. Three real bugs were found and fixed while building this, each confirmed empirically rather than reasoned through in advance -- see the dedicated simplifications list below, and `car_physics_3.py`'s own comments for the full account.

**Known, deliberate simplifications in `Elevator_System_1`** (documented inline in the YAML, not hidden):
- Dispatch reads raw call-button state, not a latched/remembered request -- a call has to still be held (or re-pressed) by the time the car is free to serve it, because a latch that drives dispatch and is also cleared by dispatch's result is a same-scan cycle.
- A second call arriving while doors are open at the first can preempt mid-dwell (Target_Floor recomputes every scan from raw inputs) -- not an issue when calls come one at a time.
- The door-obstruction hold-restart is edge-triggered: a long continuous block resets the hold once at the start of the block, not continuously for its whole duration.
- The self-oscillating TON idiom used for `Travel_Pulse` and `Clock_Pulse` is periodic but not *uniformly* periodic: the first pulse after a gating condition goes true fires after `PT` scans, but every pulse after that is `PT+1` scans apart. Measured effect: a ground-to-2nd-floor trip takes 9 scans, not the 8 a naive "4 seconds per floor" reading implies; door-hold runs roughly double the configured `Door_Hold_Time` (~12 scans instead of 6). This was discovered and behaviorally verified while validating the file against the real engine, not part of the original translation intent -- documented rather than fixed for Stage 1. See `docs/architecture.md`'s "Known limitation: self-oscillating pulses aren't uniformly periodic" for the general mechanism.
- Dispatch always serves the lowest-numbered pending call, recomputed from scratch every scan -- not what a real elevator does (real single-car dispatch is "Selective Collective" control, known in CS as the LOOK algorithm: continue current direction, serve calls along the way, reverse only once nothing's left ahead -- researched, not assumed). Confirmed by actually running it: a car mid-flight toward floor 4 reverses immediately, mid-trip, the instant floor 1 is called, rather than finishing the trip first. This can't be fixed here: LOOK dispatch needs `Target_Floor` to compare against the car's own current position, and `Current_Floor` here is a `CTUD` operation whose own `CU`/`CD` fields already read `Target_Floor` -- giving `Target_Floor` a `Current_Floor` reference too closes a real cycle, confirmed by actually triggering a `CycleError`, not assumed. Fixed properly in `Elevator_System_2`, where position stops being an operation at all.

**Known, deliberate simplifications and design decisions in `Elevator_System_2`:**
- Same raw-button-read and mid-dwell caveats as `Elevator_System_1` -- unaffected by the physics change, still true.
- `Current_Floor`/`Velocity_FloorsPerSec` are `runtime_inputs`, not `outputs` -- a physics plant writes them every scan, structurally identical to a sensor from the engine's point of view (no producer edge, same as any raw button). This is the single change everything else in this stage's story traces back to.
- `Moving`'s expression is byte-for-byte unchanged from `Elevator_System_1`, but its role isn't cosmetic anymore -- the physics plant reads it directly as its run/hold permission. Since `Moving` already included `!Doors_Open`, this closes `Elevator_System_1`'s mid-dwell-preemption gap automatically: the car physically cannot start moving on a new target until doors are shut, even though `Target_Floor` itself can still jump mid-dwell.
- LOOK dispatch (`Going_Up` direction latch, `Any_Call_Above`/`Any_Call_Below`) replaces the old lowest-floor-wins order. A real bug was found and fixed while building this: the first version compared `Current_Floor` directly against `Target_Floor` for arrival detection, but `Target_Floor` can change in the same scan the car arrives (if a call exists elsewhere), which raced against arrival detection and let the car sail through its own destination without ever opening the doors there or clearing that floor's request -- confirmed by actually tracing the scan-by-scan trigger, not guessed. Fixed with `Call_At_Current_Floor`, which checks for a pending call *at the current position* directly, independent of whatever `Target_Floor` does later in the same scan.
- Every physical constant (`Max_Velocity`, `Acceleration`, `Deceleration`, `Arrival_Tolerance`, `Velocity_Snap_Tolerance`) lives in `elevator_2.yaml`'s `physical_constants`, with the first three tracing to a stated plain-English requirement in `description_2.md` (~2 seconds to accelerate, cross a floor at cruise, and decelerate) rather than being picked arbitrarily. `car_physics.py`'s constructor has no fallback default for any of them -- a missing constant is a `TypeError`, not a silent wrong number.
- Floor count widened from 3 to 6 specifically because a short hop didn't give the trapezoidal profile enough distance to visibly reach cruise speed before braking again -- confirmed by comparing rendered velocity traces before and after, not assumed.

**Known, deliberate simplifications and design decisions in `Elevator_System_3`:**
- Door/dispatch logic is untouched from `Elevator_System_2` -- same LOOK dispatch, same `Call_At_Current_Floor` fix, same raw-button-read caveats.
- The wear model is deliberately usage-based (damping only degrades while `Moving=True`), not calendar-time-based -- matches how a real bearing or damper actually wears.
- Three real, empirically-found bugs during development (full account in `car_physics_3.py`'s comments and `description_3.md`):
  1. **Numerical instability.** The spring-damper's own natural timescale (roughly `1/omega_n`) is far finer than this project's 1-second scan convention. Integrating at 1-second resolution didn't approximate badly, it diverged outright (car position read 5.0 after one scan from a standing start). Fixed by sub-stepping the physics internally (100 sub-steps per outer scan) while still only sampling `Moving`/`Target_Floor` once per outer scan, same as every other stage.
  2. **Wrong sub-stepping target.** Holding the nominal plant's setpoint frozen for the whole outer scan while only sub-stepping the actual plant against it produced a "catch the frozen point, then sit and wait" pattern instead of smooth tracking. Fixed by sub-stepping *both* plants together, so the actual plant is always chasing a target that's genuinely still moving.
  3. **Wrong CUSUM signal.** The first design used a signed, two-sided CUSUM (separate accumulators watching each direction). It never accumulated meaningfully even with confirmed real wear present, because the wear signature (damping-driven ringing) is a symmetric oscillation around zero, not a directional bias -- confirmed by tracing a worn trip's residual directly (negative during the first part of a transition, positive during the next). A signed two-sided CUSUM's positive and negative excursions cancel against each other instead of accumulating. Fixed by switching to a single CUSUM on the residual's *magnitude*, the standard, correct tool for detecting growing spread rather than a shifted mean.
- Tuning was empirical throughout, not formula-derived, and the numbers are documented with the trace that produced them: `Natural_Frequency` went from an initial guess of 8 rad/s down to 2 (at 8, even a fully-worn system's residual peaked around 0.006 floors/sec -- barely above healthy noise -- because the system reabsorbed disturbances before underdamping could build visible amplitude). `Slack_K=0.02` and `Threshold_H=0.25` were picked by tracing the actual trip-by-trip CUSUM trajectory: a healthy run (200 simulated round trips, zero wear) never exceeds 0.0114 -- more than 20x margin -- while a worn run (`Wear_Rate=0.0015`) alarms at trip 46, right as the damping ratio reaches its floor, not dozens of trips after it was already fully broken.
- The interactive tool's Auto-Cycle toggle is off by default -- the person clicks floor buttons themselves, same as the other two stages, unless they specifically choose to speed through the many round trips this stage's story needs. Speed is capped at 5x for the same reason: this is meant to still feel like a live simulation being watched, not a batch job.
