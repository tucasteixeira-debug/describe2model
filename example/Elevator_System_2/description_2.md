# Elevator_System_2 -- design problem and requirement

Based on the initial elevator configuration (`Elevator_System_1`), it's noticeable that the logic directly owns and sets the car's position, like a counter it drives itself -- and that doesn't correspond to reality. A real logic controller doesn't have that kind of authority. It can only send signals to actuators: run the motor or don't, go up or down, stop or continue. It has no way to simply declare where the car is; it can only command a motor and read back a position sensor, the same way it reads any other input. Because the current model skips that boundary, it also skips the one consequence of it that matters most: a real motor carries momentum, so a real controller has to command deceleration *before* the target floor or the car overshoots -- a failure mode this model has no way to even represent.

So the new requirement for `Elevator_System_2` is: introduce a physical layer, separate from the logic, that the logic can only command and read from -- never set directly. The logic decides *where the car should go*; the physical layer decides *how the car actually gets there*, accelerating, cruising, and decelerating on its own terms, with position and velocity as real outputs the logic reads back rather than assigns.

That physical layer needs actual numbers to run on, and those numbers are part of the requirement, not an implementation detail to be picked arbitrarily later: the car should accelerate up to a cruising speed over about 2 seconds, cruise at whatever speed that is, and decelerate back down to a stop over about 2 seconds as well, symmetrically -- with the cruising speed itself set so that crossing one full floor at that speed also takes about 2 seconds. That's a deliberately invented, round design choice for this portfolio project (not measured from any real system, the same way Stage 1's "4 seconds per floor" was an invented placeholder rather than a measurement) -- but it's a stated one, in the same place and the same way Stage 1's timing numbers were stated, not a number that only exists as a Python default somewhere in the physics plant's constructor.

## Why this is a richer model, not just a nicer one

It would be easy to describe this stage as "the car now moves realistically instead of teleporting," and stop there. That's true, but it undersells what actually changed, and it's not the strongest reason this stage matters.

In `Elevator_System_1`, "what the logic commanded" and "what the car did" are the same variable. `Current_Floor` was a counter the logic incremented itself -- there was never a moment where the car's actual position could differ from what the logic believed it to be, because one number was doing both jobs. You cannot ask "did the car behave the way the logic expected?" of that model. The question has no meaning, because there is only one number where the question needs two.

`Elevator_System_2` splits that number into two, for the first time: `Moving` is what the logic *commands* -- go, or hold -- and `Current_Floor` / `Velocity_FloorsPerSec` are what the physical layer *actually produces* in response. Right now those two always agree; the physics plant is perfectly obedient, and nothing here yet gives it a reason not to be. But the two are now genuinely independent signals, produced by two different pieces of code, with nothing forcing them to match beyond the plant choosing to comply.

That independence is not a side effect -- it's the actual precondition for `Elevator_System_3`. A monitoring layer that catches drift (a synthetic wear parameter making the car's real behavior diverge from what the logic expects) needs exactly this: a commanded/expected value and an independently-produced actual value, with room between them for a gap to open up. `Elevator_System_1` could not host that comparison no matter how it was instrumented, because there was nothing to compare -- command and outcome were the same variable by construction. `Elevator_System_2` is the stage where that stops being true, which is a different kind of upgrade than "more realistic," even though it's the realism work that happens to be what makes it possible.

## A second, concrete example: real dispatch order

`Elevator_System_1`'s dispatch always serves whichever pending call has the lowest floor number, recomputed from scratch every scan -- not what a real elevator does, and not something anyone deliberately chose; it just fell out of a simple `if`/`else` chain. Real single-car dispatch (researched, not assumed -- the industry term is "Selective Collective" control, known in computer science as the **LOOK algorithm**) keeps going in whichever direction the car is already moving, serves every call along the way, and only reverses once nothing is left ahead of it in that direction.

`elevator.yaml` here implements real LOOK dispatch: a `Going_Up` direction latch, and `Target_Floor` picking the nearest active call ahead of the car in whichever direction that latch currently points. Confirmed behaviorally: call floor 4, and while the car is still mid-flight past floor 1, call floor 1 too -- it finishes going to 4 first, genuinely stops and opens the doors there, and only then reverses and heads down to 1. `Elevator_System_1` cannot do this: a `CycleError`, confirmed by actually triggering one, is what happens the moment `Target_Floor` is given a `Current_Floor` reference while `Current_Floor` is still a `CTUD` operation whose own fields already read `Target_Floor`. LOOK dispatch needs to compare pending calls against the car's actual position, and that comparison was never available until position stopped being something the logic drives itself -- the same structural fact the commanded/actual split above is about, showing up a second, independent time in the same stage.
